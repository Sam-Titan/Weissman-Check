What it is

You drop in a file. Six real lossless compressors (gzip, brotli, zstd, lz4, xz, bzip2, each at a fast and a strong setting) run on it, and the app tells you which one to ship, for static files or dynamic responses, at an assumed 20 Mbit/s network. It also shows a scorecard, a delivery-time chart, a Weissman score you can "break", and a replay of how LZ-style compressors find repeats. Already-compressed files (docx, zip, png…) get an "Already compressed" verdict.

Three pieces: a React frontend (frontend/src), a FastAPI backend that runs the compressors (backend/app), and the decision logic in one pure file (backend/app/analysis.py).

One action: clicking Run

  1. Click Run in the browser: run() in frontend/src/App.tsx
  2. Upload and listen: createRun and openEvents in frontend/src/api.ts
  3. Time real compressors: work() in backend/app/main.py calls run_benchmark and timed_median in backend/app/benchmark.py
  4. Decide: analyse() in backend/app/analysis.py
  5. Show: the done event sets the analysis, and RecommendationBanner, the scorecard, table and chart render it

Reference route (3 stops)

1. The click becomes a request. frontend/src/App.tsx, search async function run. It calls createRun (upload) then openEvents (stream). result events fill the progress bar; done carries the full analysis and switches to results.

2. Real compressors, timed. backend/app/main.py, search def work; then backend/app/benchmark.py, timed_median, which repeats each compress and decompress and keeps the median so one noisy run cannot decide the answer.

3. Where the answer is decided. backend/app/analysis.py: static_time (transfer + decompress) versus dynamic_time (adds compress time) is the whole Static/Dynamic toggle. _recommend picks the winner and the near-tie. weissman_cell scores a row against a baseline. _already_compressed sets the packed-file verdict.

To change this, start here

  • The assumed network speed: NETWORK_MBPS in backend/app/analysis.py (restart the backend).
  • Which compressors and levels run: the codec table in backend/app/benchmark.py (_zstd, _gzip, _brotli…) and frontend/src/lib/compressors.ts for colours.
  • The "already compressed" rules: PACKED_ENTROPY_BITS, PACKED_MAGIC, PACKED_EXTENSIONS in analysis.py.
  • How the banner words the verdict: frontend/src/components/RecommendationBanner.tsx.
  • Look and feel: frontend/src/styles.css and frontend/src/components/Window.tsx.
  • The replay card's matching: frontend/src/lib/lz77.ts.

A practice to reuse

Pin down one observable example before building, and keep the decision logic separate from I/O.

Here the spec's worked example (1,000,000 bytes at 20 Mbit/s, where brotli strong wins static and zstd fast wins dynamic) became test_worked_example_flips_between_static_and_dynamic in backend/tests/test_recommend.py. Because analysis.py is pure functions with no file or network access, new rules like the near-tie, "too small to matter" and "already compressed" each got a small test (test_packed.py) without starting a server. On another project, write the one concrete input and expected output first, then ask the agent to make it pass.
